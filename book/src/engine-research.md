**Verdict up front.** Two stacks, chosen per week, not per taste:

- **Bevy stack** — the full engine. This is the W4 stack: the thing W4 exists to validate *is* the lumen/Bevy rig path, so substituting a lighter framework would validate nothing. Cost: wasm size (see §5).
- **macroquad stack** — a small immediate-mode 2D library with first-class HTML5 output. This is the W11 stack: *Withheld* is a control-law game with minimal rendering surface (one figure, a threshold line, a countdown), and macroquad's tiny wasm keeps the single-file delivery safe while the *law* (the part that ports back) is plain Rust either way.
- Rejected for jam delivery: **ggez** (no official web target — see §2a) and **raw wgpu** (a graphics API, not a game framework; it is what Bevy sits on, not an alternative to it at jam scale).

## 4. Quality bar — Laplace3D-class minimum

The bar (estate standard, stated here as the acceptance contract for both Rust weeks): **60 fps; motion on every frame (no frozen holds outside authored beats); secondary-motion lag ≤ 17 ms behind primary; humanized jitter on held poses; expressions readable at the size the player actually sees them; loop seams ≤ 1.1 (seam metric of record); audio/animation sync +12 ms ± 25 ms; deterministic fixed-step simulation.**

| Bar item | What helps in Rust | What fights it |
|---|---|---|
| 60 fps, motion every frame | Bevy's batched 2D renderer and wgpu backend are far beyond a 2D VN's needs; macroquad's batching likewise. Fixed-step sim + interpolated render means motion continuity survives frame hitches. | Wasm single-thread constraints: wgpu's own docs note multithreaded-wasm paths are guarded/unsupported in places (https://docs.rs/rerun/0.26.2/rerun/external/eframe/egui_wgpu/index.html summarises the wgpu position). Budget CPU per frame as if single-core — because in the browser, it is. |
| Secondary lag ≤ 17 ms; humanized jitter | Tween/spring layers (bevy_tween) driven *from the fixed step*, with lag implemented as a sim-side spring — deterministic, measurable, identical native and wasm. Jitter is a seeded noise channel in the sim, never `Math.random`-equivalent at render time. | Render-side tweens (wall-clock) drift from the sim and break both the lag budget and determinism; both tween crates default to wall-clock thinking — the discipline is ours to impose. |
| Expression readability at size | Atlas resolution + the face-channel system (§3): readability is an art/gate property (D-221 visual evaluation on final-artifact crops), not a renderer property. | Texture compression for the size budget (§5) can smear exactly the small features (pupils, blush edges) readability depends on — compression settings are gated on face crops, not on file size alone. |
| Loop seam ≤ 1.1 | Fixed-step evaluation makes loops *exactly* periodic when authored so; seam is measured by the estate's evaluator on the shipped build. | Yarn/audio/event-driven loops that key off wall-clock events can re-introduce seam drift; looped beats are sim-clocked. |
| Sync +12 ms ± 25 ms | Kira's clock system exists precisely for beat-timed audio events (§2c); sim emits audio events on step boundaries, kira schedules against its clock. | Browser audio latency varies by platform; the budget is met by scheduling *ahead* (the +12 ms bias is the design centre), and verified by the metrics harness — never by ear in CI (silence rule). |
| Deterministic fixed-step | **Evidence, honestly stated**: the lumen rig runtime is already byte-deterministic on its fixed-step evaluation (estate record: rig-core/rig-import/factory suites green at landing, bake determinism hashes recorded for the mocap lane). The jam inherits the pattern, it does not re-prove it. | Floating-point and iteration-order discipline: no hash-map iteration in sim order paths, no wall-clock reads inside `FixedUpdate`, seeded RNG only. Clippy + replay-hash tests enforce. |

## 5. Risks & seams

1. **Wasm bundle size is the binding constraint of the whole Rust jam delivery.** Bevy's floor is an order of magnitude above macroquad's (§2a). Base64 inlining multiplies whatever we ship by ~1.37, and the browser must parse the resulting single HTML file. Mitigations, in order: trim Bevy features to the 2D set (drop PBR/3D/audio defaults not used); `opt-level = "z"`, LTO, strip, `wasm-opt -Oz` after wasm-bindgen; KTX2-compressed atlases; ogg audio at speech bitrates; embedded assets audited like code (every megabyte names its owner). **The packager enforces a size budget as a build gate** (W4's budget is set at its preflight from a measured hello-scene build — we do not guess the number here; the cheat-book figures are Bevy 0.12-era and are cited as a warning, not as our measurement).
2. **Bevy version churn.** Bevy breaks APIs between releases and its plugin ecosystem version-tracks it (every plugin in §2 carries a pairing table). One pinned Bevy for the whole program; plugin versions locked in `Cargo.lock`; an upgrade is a program-level event, never a per-week one. Yarn Spinner's WIP status and seldom_state's pairing table are the sharp edges.
3. **WebGPU vs WebGL2.** Bevy can render via WebGPU in the browser (https://bevy.org/news/bevy-0-11/) with a WebGL2 fallback feature; browser WebGPU coverage is not universal. The jam shell must feature-detect and fall back — and the fallback build is a second size/compat measurement at preflight, not a hope.
4. **Spine's license is a real cost line.** bevy_spine's code is permissively licensed, but the Spine Runtime License Agreement governs use (its docs say so). If the estate's Spine position (lumen format target) is not settled by the week that wants it, that week uses lumen-rig/atlas playback instead. The jam never blocks on a license.
5. **AudioContext autoplay policy.** Browsers start audio contexts suspended; kira/rodio cannot restart them without a user gesture (an old bevy_kira_audio readme calls this out explicitly). The JS shell owns the "press to start" gate that resumes audio — which the jam's ≥6-screen structure already requires as a Title screen interaction.
6. **Determinism leaks through the platform layer.** `localStorage` persistence (bevy_pkv), asset decode order, and browser timer behaviour all sit outside the sim. The sim crate takes inputs as data (tapes, seeds, tables) so replay tests run headless in `cargo test`, where the estate's gates actually live.
